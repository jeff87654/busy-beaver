# Three pitfalls of this development (and a few sandbox notes)

## 1. `execute` is cubic in the number of steps

busycoq's `execute` tactic is

    Ltac execute := introv; repeat (try solve [finish]; step).

`step` ends in `simpl_tape`, i.e. `autorewrite with tape_pre; simpl; autorewrite with tape_post`,
and `autorewrite` rewrites **the whole goal** — which, in the middle of an `execute`, contains
the entire proof term accumulated so far, i.e. every intermediate tape.  So one monolithic
`execute` over *n* steps performs O(n²) tape rewrites over tapes of size O(n): it is cubic.

The fix is to cut the run into chunks.  `BB44_start.v` (generated by `../tools/gen_start.py`)
states the intermediate configurations explicitly and proves 10 chunks of 10 steps each:

    Lemma chunk_0 : cfg_0 -->* cfg_10.
    Proof. unfold cfg_0, cfg_10. execute. Qed.

Inside a chunk the accumulated term stays short, so the cost is linear; the whole file
compiles in 5 s.  The chunks are then joined with `follow`.

Note that `follow` is "peeling": `follow H` on a goal `c1 -->* c3` uses `evstep_trans` and
leaves the goal `c2 -->* c3`, so the last chunk must be closed separately with `finish`.

## 2. `g 509` must never be evaluated

`g` is

    Fixpoint g (k m : nat) : nat :=
      match k with O => S m | S k' => Nat.iter (2 * m + 2) (g k') 0 end.

`g 509 x` iterates `g 508` `2x+2` times, so getting *any* normal form of `g 509 x` requires
normalising `x` as well.  For `x = g 509 (g 509 (g 509 0))` this is astronomically expensive:
even a single `whnf` of `Nat.iter 1 (g 509) 0` already runs into the billions of reduction steps.

Concretely, the following all take minutes or exhaust the memory, while the whole proof
otherwise takes 25 s:

- `simpl` on any goal mentioning `g 509` (it normalises the whole tree, exponentially);
- `lia` on a goal mentioning the raw `Nat.iter 1 (g 509) 0` (it partially unfolds the two
  occurrences into *different* terms, so the hypothesis and the goal no longer match and
  `lia` reports "Cannot find witness");
- `apply`/`exact` with a *conversion* between `g509` and the raw `Nat.iter 1 (g 509) 0`
  (unification expands the iter, the comparison of the two trees is quadratic).

Three precautions make the development robust:

1. **Seal `g509`.**  `g509` is introduced through a `sig`
   (`g509_spec`, `g509`, `g509_eq`), so `simpl` and `lia` treat it as an opaque atom and never
   try to evaluate it.  `g509_eq : g509 = Nat.iter 1 (g 509) 0` is proved by `exact`, whose
   conversion check stops at the `proj1_sig` match.

2. **Never compare `g509` with the raw term.**  Every configuration that mentions the score
   mentions it through the *same* term `g509`, so all comparisons are syntactic.  Where the
   raw term is unavoidable — the result of `B_rule` — the result is abstracted away first:

       Theorem B_rule_gen : forall k n m r (x : nat),
         x = Nat.iter n (g k) m -> Bcfg (S k) n m r -->* Bcfg (S k) 0 x r.

   and instantiated with `x := g509`, whose hypothesis `g509_eq` matches syntactically.

3. **Do the arithmetic generically.**  The counting lemmas are stated for an abstract `x`
   and only instantiated afterwards (`cells_count`, `cells_nonblank`), so that no tactic ever
   looks at `g509`.  The final score uses `score_generic : 2x+4 = K -> 2x+514 = K+510` with
   `x := g509`, `K := knuth 509 2 3`.

`knuth 509 2 3` (= 2 ↑^509 3) is not a problem in the same way: `knuth`'s iteration count is a
literal, so unfolding it costs only O(2^508) nodes, and `lia` treats it as an atom.

## 3. A block of symbols has two shapes

busycoq writes a left stream as a list (nearest first) followed by an infinite stream of
blanks, `xs *> const 0`.  When a block of identical symbols is written as

    [c]^^p *> (c >> x)            (the extra c at the *back* of the block)

and elsewhere as

    [c]^^(S p) *> x               (the extra c at the *front*)

the two denote the *same* stream, but Coq does not see that: the first has to be `tl`-ed
before its head is known, and `tl` of a block with a symbolic length is stuck.  This shows
up in the two BB(4,4)-specific phases, where a sweep turns a block of 3s into a block of 2s
and the head then steps onto the new block.

The lemma `block_snoc` bridges the two shapes:

    Lemma block_snoc : forall (c : sym) (p : nat) (x : Stream sym),
      ([c]^^p *> (c >> x)) = ([c]^^(S p) *> x).

It is proved by rewriting with `Str_app_assoc` and `lpow_shift`, and it is used three times
in `D_phase_p` (`rewrite (block_snoc 3 p (const 0))` and twice with `c := 2`).  Without it
the goals of the phases do not even typecheck against the sweep lemmas.

## 4. Sandbox notes (only relevant on FUSE/"oss"-style mounts)

1. **`TMPDIR`**: Coq writes `.vo` through the temp directory.  If `/tmp` is not writable,
   `coqc` fails at the very end with `System error: "X.vo: No such file or directory"`.
   Fix: `export TMPDIR=/some/real/dir`.
2. **`.vo` pre-creation**: on such mounts, `Sys.file_exists` could report a stale positive for
   `.vo` files, making Coq's delete-then-recreate fail intermittently.  Fix: `touch X.vo`
   right before `coqc X.v`.
3. **Numerals**: `0`–`3` are sym notations (`Open Scope sym` in `Individual44.v`), so bare
   numerals in `nat` positions occasionally parse as syms; the sources use `0%nat` where that
   happened.
4. **Stream cons**: `::` is the *list* cons, not the stream cons.  A stream is built with
   `>>` (or `:`>`), e.g. `2 >> ([3]^^m *> const 0)`.
